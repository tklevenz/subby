# Project Handoff & Context Specification: Subby

## 1. Project Overview
Subby (repo `tklevenz/subby`) is a local-first, offline-capable baby/child activity tracking mobile application (logging feeds, diapers, and sleep/wake windows) built within a `pnpm` monorepo (`~/src/kindred-log`)[cite: 4].

**Name and brand:** the app is called **Subby** (store title "Subby: Private Baby Tracker"); the repo is `github.com/tklevenz/subby` (renamed from `kindred-log` 2026-11-09; the local checkout may still be `~/src/kindred-log`); the workspace packages are `@subby/shared`, `@subby/mobile` and `@subby/server` (renamed from `@kindred-log/*` 2026-11-08), the root package `subby`. The mark is a yellow submarine with a crescent moon in its big porthole, on navy (`#0E1B3D`), wordmark in Fredoka. Design canvas row "Subby 1 in the app" maps where the brand goes on every screen; on Home the brand lives only in the sleep tile and its Undo bar (canvas row "Subby on Home").
- Domain: **subby.baby** (bought 2026-11-05). The hosted Subby Sync runs at `sync.subby.baby` (since 2026-11-06); self-hosting docs keep `sync.example.com`.
- Everything is called Subby. The old internal names were dropped in one clean break before launch (2026-11-08), which made every earlier family, recovery key and synced record unreadable. From now on these are frozen, because changing them breaks existing data: the `subby/…` crypto labels (signatures, the device log, sealed keys, records, and the recovery words' identity, pinned by its test vector), the `subby:` QR prefix, `BACKUP_FORMAT = 'subby-backup'` (`readBackup` also accepts the old `kindred-log-backup`; keep that), `subby.db` and the `kl.*` SecureStore keys, the `subby` URL scheme, the background task names, and on the server the `subby-sync` service id and the `subby` Postgres user and database.
- The package id is **`baby.subby.app`** (Android package and iOS bundle id, since 2026-11-08; before that `com.kindred.log`, a different app: phones moving over reinstall and restore from a backup or re-join sync). Never change it again after the first store release.

## 2. Tech Stack & Environment
- **Monorepo / Package Manager:** `pnpm` workspaces (Turborepo / `pnpm run dev` task runner)[cite: 4]
- **Mobile Framework:** Expo SDK 57 (recently upgraded from an earlier SDK to match the latest Expo Go client)[cite: 4]
- **Core Libraries (SDK 57):** React 19.2.3, React Native 0.86.3, TypeScript 6, `expo-router` ~57.0.28, Reanimated 4.5.1 / Worklets 0.10.1, New Architecture enabled. Use `npx expo install <pkg>` (not `pnpm add`) for anything Expo-managed; verify with `npx expo install --check`.
- **Styling:** NativeWind v4 (`nativewind/babel` preset) + Tailwind CSS. Dark only for launch (slate ground, muted cards, pastel accents), but built for themes:
  - `apps/mobile/theme/palette.js` is the single source of every UI color, by role (`ground`, `surface`, `raised`, `line`, `ink`/`inkMuted`/`inkFaint`…, and per hue `violet` (500, for tints and borders with opacity), `violetSoft` (300), `violetPale` (200), `violetStrong` (400), `violetDeep` (600), `violetFaint` (100); plus `avatarNBg`/`avatarNInk`).
  - `tailwind.config.js` replaces Tailwind's palette with these roles as CSS variables: write `bg-surface`, `text-ink-muted`, `border-violet/40`, never `bg-slate-900` (raw palette classes no longer exist and silently do nothing).
  - Color props in JS (icons, charts, navigation) use `colors.<role>` from `theme/colors`, read at render time (no module-level copies; `TYPE_META.color` is a getter). No hex literals except data colors (diaper swatches).
  - `theme/palette.test.ts` fails on raw palette classes or hex literals in `app/`, `components/`, `features/`.
  - Adding a theme later: add a map next to `dark` with the same keys (the test checks), switch the CSS variables (NativeWind `vars()` or a `.dark:root`/class block) and swap `colors`.
- **State & Local Persistence:** Zustand (in-memory UI state) backed by `expo-sqlite` via `drizzle-orm/expo-sqlite` (SQLCipher-encrypted in native builds, plain in Expo Go), with Drizzle migrations (see §3 DB).
- **Runtime Environment:** Node.js v24.9.0 on macOS (Apple Silicon)[cite: 4]

## 3. Repository & File Structure

Roadmap: see `PROJECT.md` §5. The feature-parity plan (Huckleberry + Baby Buddy, phases 1–6) is summarized there.

### `packages/shared` (`@subby/shared`, consumed as TS source)
- `src/schemas/log.schema.ts`: `LogEntry` + discriminated `LogPayload` union (feed, diaper, sleep, pumping, growth, temperature, medication, potty, activity, milestone, note). Canonical units only: ml, g, cm, °C, seconds, epoch ms.
- **`endedAt` rule:** for `TIMED_LOG_TYPES` (sleep, feed, pumping, activity), `endedAt` is always set once the entry is complete (= `startedAt` for instant ones like a bottle), and `null` means a running timer. For other types it's always `null`.
- `src/schemas/child.schema.ts`: `Child`.
- `src/crypto/` (import from `@subby/shared/crypto`): end-to-end encryption for sync, shared by the app and the server.
  - Built on the audited `@noble/*` and `@scure/bip39` libraries. Never hand-roll primitives, and never use `Math.random` for keys.
  - React Native must call `setRandomSource` with `expo-crypto` at startup.
  - Contents:
    - `aead` (XChaCha20-Poly1305).
    - `keys`: device identity (Ed25519 sign + X25519 box) and sealed boxes.
    - `recovery`: 24 words to an identity. Its test vector must never change, or existing recovery keys stop working.
    - `pairing`: the 6-digit code.
    - `deviceLog`: the signed, hash-chained family membership (`subby/devicelog/v1`). Every client verifies it.
      - It also records every family key epoch. `create` (epoch 1) and `epoch` entries carry `keyHash = epochKeyHash(epoch, key)`, a commitment to the key.
      - Sealed boxes are anonymous, so the server could seal a key of its own. Phones therefore open keys only with `openFamilyKey`, which checks the commitment, and take the current epoch from the log (`state.epoch`), never from the server.
      - `assertLogContinues` rejects a log older than the one a phone already saw (`settings.sync.logSeen`), because a server could otherwise serve a prefix that hides a removal or a newer epoch.
      - Only devices start epochs, one at a time; the recovery key can only `add`.
      - `state.rotationDue`: a removal, or a replaced or cleared recovery key, owes a new epoch.
      - `epoch` entries carry `closedSeq`: the sync seq the rotating phone had pulled to (the server checks it's the family's latest). Records of older epochs end there (`state.closedAt`, `withinEpoch`), so a removed phone writing with a key it still has, stored by a hostile server, is refused. Signed only when set, so older entries keep their signatures; an epoch without one closes nothing.
      - A phone that joins later can't tell such records from genuine history (the seq isn't signed per record); phones that were in sync can.
    - `files`: chunked photo encryption.
- `src/i18n/` (`@subby/shared/i18n`, A14): our own small i18n, no library (shared needs it too, and Hermes' `Intl.PluralRules` isn't relied on).
  - `en.ts` is the source catalog: flat dotted keys by area (`'home.tapSleep'`), `{name}` placeholders, `{ one, other }` plurals picked by `{count}` (`pluralCategory`: French and Portuguese count 0 as one). `t(key, params)` formats number params for the language, so pass years and ids as strings.
  - Other languages (`de`, `es`, `fr` (vous, French spacing), `it`, `nl`, `ptBR`; German, Spanish, Italian and Dutch use du/tú/tu/je, Portuguese você) go in `catalogs.ts` (`TRANSLATIONS`, every language required), typed `Translation` (every English key). Model-drafted, reviewed by independent model passes (back-translating the `review.ts` texts) and a Gemini pass; the user settled German and Dutch and accepted the rest on 2026-11-10. Adjust from user feedback; give new `review.ts` texts the same back-translation check. A new English key needs all six translations, or typecheck fails. `i18n.test.ts` checks keys, placeholders and plurals per language, and that `review.ts` (`REVIEW_KEYS`: safety texts a native speaker reviews per language) only names keys that exist. A missing key falls back to English at runtime.
  - `formatNumber`, `formatDate(ms, Intl options)`, `formatClock(ms, clock)` use the current locale; never `toLocaleString([])` or `toLocaleDateString([])`.
  - Shared domain text goes through `t()` too (durations, ages, reminders, family alerts, milestones (`label` is a getter), story, feed/diaper summaries, backup and invite errors). Percentile ordinals: English computes "50th", other catalogs wrap the number in `percentile.*`.
  - Stays English: CSV headers (decided), the diagnostics report, server error messages, the dev tools in `SyncAccess`.
- `src/sync/` (`@subby/shared/sync`):
  - `envelope`: `sealRecord`/`openRecord`. Metadata is bound to the ciphertext as AAD.
    - Tombstones carry a sealed empty body: no content stays on the server, but a server can't delete on its own. `openRecord` throws `UnsealedRecordError` for one without data (older apps sent those); phones skip them.
  - `merge`: last-writer-wins with a device-id tie-break, the same rule on server and client.
  - `clock`: last-writer-wins goes by phone clocks, so a wrong one loses edits. Pulls carry the server's `time`; `clockOffset`/`clockOff` (> 5 min) set `useSyncStore.clockOff`, shown on Home (`SyncStopped`) and the Sync screen. The server refuses records dated more than `MAX_CLOCK_AHEAD_MS` (a day) ahead as stale; the app re-dates pending rows from the future before pushing (`redateFutureEdits`).
  - Plan: `~/.claude/plans/let-s-analyze-the-current-precious-scroll.md` (Phase 2).
- `src/domain/`: pure, RN-free helpers. Put new business logic here and test it with vitest (`src/__tests__`). The tests run with `TZ=Europe/Berlin` (package.json), so `dst.test.ts` and other DST cases cross real clock changes on any machine. Time rules: store epoch ms, measure durations as differences, step days with `addDays`/`startOfDay` (never + 24 h), read habits off the wall clock.
  - `units` (`formatDose`: "1 drop"), `time` (`formatDuration` for live timers, with seconds; `formatSpan` for finished entries, no seconds from a minute up; a zero part is dropped: "2h"), `summary`, `validate` (`isCompletePayload` gates Save).
  - `feedTimer`: breastfeeding L/R timer state lives in the feed payload (`timerSide`, `timerSideSince`); `toggleSide`/`pauseFeed`.
  - `recent` (food/medication suggestions, `medicationsDue` (with the last dose, to log the next like it), `pumpingDue` (the pumping reminder's time)), `milestones` (bundled checklist).
  - `stats` (`dailyStats` per-day totals, splitting sleep across midnight; `averageStats` over tracked days; `sleepSegments`; `solidsReport`; DST-safe `addDays`/`dayRange`).
  - `growth`: WHO LMS z-scores/percentiles (0–24 months, from the birth date; corrected age for preterm babies was dropped on purpose, and `dueDate` is stored but unused), `percentileCurves`. The tables in `domain/who/lms.ts` are generated from the CDC-hosted WHO CSVs; don't edit them by hand.
  - `prediction`: on-device nap prediction. Age norms (`ageNorms`), plus `sleepHabits` (the last 7 days; night sleep logged in pieces is merged into one night), `predictNextSleep` (put-down window, ±30 min from personal data, plus `napMinutes`, the expected nap length; nothing while `isNightWaking`: awake after a night sleep that ended ≥90 min before the usual wake-up, until that wake-up or 3 h, after which it was the day's start) and `suggestedSchedule` (today's logged wake-up, naps and started bedtime as `logged` items, the rest predicted from the last one; a nap that would run into bedtime is left out: one starting within 90 min of it, or ending without ¾ of the shortest wake window left). Bedtime is the baby's usual one, else the age norm's (`AgeNorms.bedtime`, 19:30 from 3 months), so a day without history no longer ends mid-afternoon. Under 3 months, until a few nights are logged, there's no planned day (`planned: false`) and no bedtime: `predictNextSleep` gives `kind: 'sleep'` ("Next sleep", no nap number; null once its window has passed, since newborn naps go unlogged; with logged nights, null until bedtime is next instead of jumping to it), and the Schedule screen explains that newborns don't keep a schedule yet. With logged nights, a newborn's day fills with naps up to the bedtime (the logged nap count is ignored, since newborn naps go unlogged). `defaultNap` is the default nap flag (Home's sleep tile, and the log sheet until the toggle is used): night from an hour before the usual bedtime until the usual wake-up, else `isNapTime` (07–19h) until enough nights are logged. Heuristic, verified against the real Baby Buddy history. Replayed on two years of real sleeps (2026-10-28): longer windows (14–28 days, or recency-weighted) and predicting naps by clock time were no better than 7 days; a nap counts while ≥30 % of days have it (`NAP_DAY_SHARE`).
  - `timeline`: `dayTimeline` (History's Day: entries newest first, a sleep running into the day from the evening before, wake windows of a minute or more between sleeps, today's current one first; a night with wakings is one `night` item).
  - `nights`: a night is stored as its pieces, never as one entry with wakings inside. `groupNights` puts night sleeps (not naps) less than `NIGHT_GAP_MS` (3 h) apart into one `Night` (pieces, wakings, time asleep, longest stretch); prediction merges nights by the same rule. `nightPieces` turns an edited bedtime, wake-up and wakings back into pieces; `nightsByDay`/`averageNights` feed Trends (each day's night is the one that ended that morning).
  - `summary` also has `overlappingSleep` (a sleep may not overlap another; running ones last until stopped). The log sheet and the edit screen block overlaps via `apps/mobile/features/sleepOverlap.ts` (a week of sleeps from SQLite plus the loaded ones).
  - `reminders`: `planReminders` (pure) turns `ReminderSettings` + per-child state into the notifications to schedule (stable `kl:` ids).
  - `familyAlerts`: what to show or withdraw when a pull brings sleeps another phone logged (`kl-family:sleep:<id>`, one per sleep or night, so "woke up" replaces "fell asleep" and an undone sleep takes it away). Naps by default; bedtime and the morning only when asked; never night wakings, nor anything over 10 min old.
  - `story`: `childStory` builds a child's story of firsts (milestones, measurements, first solid food, birth), newest first. No counts or completion: we don't gamify childcare.
  - `csv`: `logsToCsv` (one file, mixed types, only used columns, formula-injection safe).
  - `backup` (import from `@subby/shared/domain/backup`, kept off the main index):
    - The file is a zip (`fflate`) holding `backup.json` (children, entries and tombstones) plus `photos/<n>.<ext>`. Photo names are ours, never taken from row data. Device-local fields stay out: photo paths, `photoBlob`, sync status.
    - An optional passphrase encrypts it: `KLBK` header with scrypt parameters and salt, then `encryptFile`. The parameters are read from the header and bounded (≤ 64 MiB of scrypt memory).
    - Reading unzips only `backup.json` and `photos/<n>.<ext>`, and refuses a zip that would inflate past its size + 64 MiB.
    - `readBackup` validates each row and skips (and counts) bad ones; payloads are checked with `LenientPayloadSchema` (log.schema: each known field's primitive type and required fields, no value checks, unknown fields pass).
    - `planRestore` uses newest-edit-wins, like sync, after keeping one version per row (the newest, live or deleted). What was deleted here since the backup is offered separately (`plan.revive`, dated after the deletion so sync spreads it; an entry only with its child, so a deleted child comes back with its entries), and only restored when the person turns on "Bring them back" in the preview (off by default: with sync it comes back on every phone).
  - `babybuddy`: Baby Buddy record types, `mapRecord` (BB → payload), `detectUnits` (BB stores no units; e.g. weight may be g or kg), `bbRef` import refs.

### `apps/mobile`
- **Config:**
  - Minimum iOS 17.0 (`expo-build-properties` `ios.deploymentTarget` in `app.json`): the pods are built for Xcode's recommended minimum (17.0 with Xcode 27), so the app can't claim 16.4. Raise it with the Xcode toolchain.
  - `app.json`: name Subby; icons and splash from `assets/` (see below); plugins `expo-router`, `expo-splash-screen`, `expo-sqlite`, `expo-secure-store`, `expo-camera` (QR scanning; no microphone), `expo-notifications`, `expo-background-task`. No system date picker (see `DateTimeField`).
  - **Brand assets:** `assets/brand/*.svg` are the sources; the PNGs in `assets/` are rendered from them at their declared size (we used `@resvg/resvg-js`, outside the repo). Re-render after editing an SVG, then prebuild. `icon` (full bleed, iOS rounds it), `adaptive-icon` + `adaptive-icon-monochrome` (Android, framed inside the safe zone), `splash-icon` (same framing, so Android 12+'s round mask doesn't clip it), `notification-icon` (white, tinted `#FFC93C`), `tile` (rounded, for in-app use).
  - The native splash stays up until the database is open (`SplashScreen.preventAutoHideAsync` in `_layout`, hidden after `appReady()`), so there's no spinner at start.
  - `babel.config.js`: `babel-preset-expo` with `jsxImportSource: 'nativewind'`, `nativewind/babel`, and `inline-import` for `.sql`.
  - `metro.config.js`: `withNativeWind(... './global.css')`, plus `sql` in `sourceExts`.
  - pnpm note: `react-native-css-interop` must stay a direct dependency or Metro can't resolve the NativeWind JSX runtime.
- **DB:**
  - `db/schema.ts` (Drizzle): tables `children`, `logs` (generic, JSON `payload`, `ended_at`, `import_ref` unique), `settings` (kv), `reminders`.
  - `db/client.ts`: `initDatabase()` runs migrations at startup and upgrades pre-migration v0 databases via `db/legacy.ts`.
  - **Encryption:** `app.json` sets `expo-sqlite` `useSQLCipher`. `openAppDatabase()` opens `subby.db` with a random 256-bit raw key from `expo-secure-store` (`kl.dbKey`, `AFTER_FIRST_UNLOCK`). The startup decision is the pure `planOpen` in `db/encryption.ts` (tested):
    - The pre-encryption plain `subby-plain.db` is copied in once with `sqlcipher_export`, then deleted. Every step is safe to re-run after a crash.
    - An encrypted file whose key is missing (e.g. Android restore) is moved aside as `subby.unreadable-<ts>.db`, never deleted.
    - Expo Go has no SQLCipher (`PRAGMA cipher_version` is empty) and keeps using plain `subby-plain.db`.
    - Never log or export the key. Inspect a device database with `sqlcipher`, not `sqlite3`.
  - **Schema changes:** edit `db/schema.ts`, then `cd apps/mobile && npx drizzle-kit generate --name <change>`. Commit the generated `db/migrations/*`, and never edit an applied migration.
- **Stores (Zustand, write-through to SQLite):**
  - `useLogStore`: date-windowed load + `loadOlder`, `addLog`, `startTimer`/`stopTimer`, `updateLog(id, {payload?, startedAt?, endedAt?})`, `softDeleteLog` (keeps only id and type: the payload becomes `{type}`), `getLog`. Update, delete and `getLog` work for entries outside the loaded window too (falling back to SQLite). `revision` is bumped on every write.
  - Note photos are deleted from disk when their entry is deleted or the photo is replaced (`features/photos.ts`).
  - `queries.ts`: `fetchLogs(childId, {from, to, types, where})` reads SQLite directly; `useLogQuery` re-reads on every `revision`. Use these for anything beyond the store's 30-day window: History day/week, Trends, Growth, Solids, Export, and all-time lookups such as allergens in `FoodPicker` and milestones done. `HAS_FOODS` filters feeds that have foods.
  - `useChildStore` (`deleteChild` turns the child's logs into scrubbed tombstones, deletes its reminders and photos, and leaves a scrubbed tombstone row), `useSettingsStore` (units, clock, activeChildId…; `set` updates memory before the DB write, so back-to-back read-modify-writes like `saveSync` don't lose each other's changes, and `null` deletes the row because `value` is NOT NULL), `useActiveChild`.
- **Routes (expo-router):**
  - `app/_layout.tsx`: DB init + hydration; `Stack.Protected` sends users to `onboarding` when no child exists.
  - `app/(tabs)/`:
    - `index`: Home: `components/home/HomeTiles` shows Sleep, Feed and Diaper as big tiles. The pinned tile sits on top (sleep by default; long-press a tile to pin it; `settings.homeTop` per child) and the other two side by side. Below: what's due, each with a button (medication doses with a next-dose interval: Log, prefilled; pumping when its reminder is on: Start, with Undo; shown until 12 h past due), then links to the sleep schedule and today's log. Everything without a tile is the round + in the header, next to the child (canvas row "Home · only the +", D; it replaced the recent-category shortcuts). Running pumping/activity timers show above the tiles via `ActiveTimers`.
      - Awake in the night (`isNightWaking`), the sleep tile shows how long they've slept tonight instead of a prediction; no separate label or "up for the day" button (canvas row "Nights").
      - Tapping the sleep tile (start or wake up) offers Undo for 5 s; a running sleep has a Discard button (with a confirmation). Accidental taps on the big tile are easy.
      - Tapping a tile's time or the lines under it opens its entry (running, or the last one). The tile's action is a full-size `Pressable` underneath, with the content on top passing taps through (`pointerEvents`); buttons nested inside a `Pressable` don't reliably get their own taps on Android.
      - The header (`components/TabHeader`, also on History and Trends; not Settings): the avatar opens the child's profile, the name switches child (`ChildSwitcher`), the round + opens "Log something". No screen title there: the tab bar names it.
    - `history`: one day (`components/history/DayLog`): the day as a timeline, newest first: times on a rail, sleeps as thick spans, the wake windows between sleeps (`dayTimeline` in shared), a night with wakings as one block (`NightBar`, wakings listed when opened, tap to edit), plus the day's totals; arrows move by day; tapping the date opens `datetime/CalendarSheet` (month grid, Monday first, a dot on days with entries, swipe or arrows between months; `monthGrid` in `datetime/parts.ts`), and "Back to today" returns. (The Week view was dropped: Trends has the same totals.)
    - `trends`: 7/14/30-day averages and charts. A Nights section (time asleep, wakings, longest stretch, awake at night) appears once wakings are logged in the period.
  - `app/schedule.tsx` (next sleep + suggested day; linked from Home's "Sleep schedule" row), `app/reminders.tsx`.
  - `app/growth.tsx` (WHO chart, share as PNG via view-shot + expo-sharing), `app/solids.tsx`, `app/export.tsx` (CSV).
  - `app/backup.tsx` (Settings → Backup & restore; also linked from onboarding, not route-guarded), backed by `features/backup.ts`:
    - Back up: everything on the phone into one file.
      - Android saves straight to the public Downloads folder through the local native module `modules/subby-downloads` (MediaStore, Android 10+, no permission; autolinked, so changing it needs a prebuild). Android's folder picker doesn't allow Downloads itself.
      - iOS opens the share sheet, which has "Save to Files".
      - The cache copy is deleted afterwards.
    - Restore: pick a file with `File.pickFileAsync` (no document-picker package), preview, then merge in one transaction. Restored rows are `pending`, so they sync.
    - The screen waits a frame before working (`nextFrame`), since zip and the transaction are synchronous and would block the loader. Without children (a fresh install) only Restore is shown.
    - An import ref already used by another row here is dropped from the restored row.
  - `app/entry/[id].tsx`: edit/backdate any entry. A finished night sleep opens as its whole night (`components/NightForm`): bedtime, wake-up, the wakings (add, edit, remove), notes; saving reuses the pieces in order, adds or deletes the rest (a removed waking joins two pieces; their notes move to the first). Pieces that touch (a zero-length waking) open without that waking, so saving joins them. Mostly used the morning after: log the night as one, split it later.
  - `app/child/new.tsx`: add a child (modal).
  - **No feature gates** (removed 2026-11-05): the app is free and complete, any number of children. Only syncing on the hosted server is paid (PROJECT.md §3); never add a paywall in the app.
  - `app/child/[id]/index.tsx`: the child's profile page (no stack header). Full-width photo cover with name and age, a growth chart (Weight/Length/Head, WHO band), and the story of firsts (`childStory`).
  - `app/child/[id]/edit.tsx`: edit details; the danger zone deletes a child after the user types its name.
  - Settings shows children as an avatar strip linking to their profiles. App-wide settings stay in Settings.
  - `app/import/babybuddy.tsx`: import wizard (connect → review children/units → progress → summary). Not route-guarded, so onboarding can link to it.
- **Components:**
  - `charts/`: hand-rolled with `react-native-svg` and Views (no chart library): `BarChart` (stacked), `GrowthChart`.
  - `ChildSwitcher` (avatar, switch child, open a profile), `ActiveTimers`. Entries open from History or the Home tiles; delete only from the entry screen.

The CC BY 4.0 credit is at the bottom of Settings; keep it.

There's no re-pull from 0.

When the server's log is exactly the start of it (`entriesToRestore`), `refreshMembers` gives back the missing entries (`POST families/me/log/restore`), signed as they were; `heal` then grants the epochs members lack. ### `apps/server` (`@subby/server`, Subby Sync; **AGPL-3.0**, everything else is MIT)
- **What it is:** a zero-knowledge sync relay. NestJS 12 (Fastify 5; the Fastify adapter pins its fastify version, so keep the direct `fastify` dependency equal to it) + PostgreSQL via Drizzle (`drizzle-orm/postgres-js`).
  - The server stores only ids, public keys, signatures, versions and ciphertext. Never add a column that holds readable user data.
  - The HTTP contract is `packages/shared/src/sync/protocol.ts` (zod 4: use `z.uuid()` and `.loose()`, not the deprecated `z.string().uuid()` and `.passthrough()`). The server validates with `parse()` (`src/common/validate.ts`); the app uses the same types.
- **Endpoints (`/v1`):**
  - `info`.
  - `auth/challenge` + `auth/verify`: the device signs `authMessage(challenge)` and gets a bearer token. Sessions are stored hashed. `verify` re-checks membership (or the current recovery key) under `lockFamily` (`db/lock.ts`), so a phone removed after its challenge gets no session.
  - `families` (create) and `families/me/log`: the signed device log. The whole chain is verified with `verifyDeviceLog` on every append. Adds, removes and setRecovery update `devices` and `sessions`.
  - `families/me/log/restore` (devices only): entries a phone verified that a restored server lost, epochs included (their keys come by grant); they must continue the log and pass the chain checks.
  - `DELETE families/me` (any member, or the recovery key): deletes the family row (every table cascades from it) and its photo files, and closes its live sockets. A `remove` that leaves no active phone does the same, recovery key included. Nothing of a deleted family is kept.
  - `keys`: `GET`, `grant`, and `rotate`.
    - A rotation is the signed `epoch` log entry plus the key sealed to exactly the current members plus the recovery key, stored in one transaction. `families/me/log` refuses `epoch` entries.
    - Its `closedSeq` must equal the family's seq, otherwise 409 ("Pull first"); it's required.
    - Grants never overwrite an existing sealed key.
  - `invites`: create, `:id`, `:id/claim`, `:id/status`. The QR secret never reaches the server, only the hash of a derived claim key.
  - `blobs/:id` (PUT/GET, `application/octet-stream`, ≤ `MAX_BLOB_BYTES`): encrypted photos in a `BlobStore` (`BLOB_STORE=disk`, default `./data/blobs`, or `s3` for any S3-compatible storage). A push links each record's listed `blobs`; blobs a record stops listing, and all of a tombstone's, are deleted; unlinked uploads are swept after a day. A record without `blobs` (older app) keeps its links. A record can only link unlinked blobs or its own. Ids are lowercased (Postgres returns them so, and deletes use those). The allowance check and the id claim run under `lockFamily`. An upload claims its id with the row first, so a taken id is refused before the file is touched. `Entitlements.canStore` is the hosted quota hook.
  - `sync/push` and `sync/pull`:
    - Last writer wins via `serverAccepts`, and a per-family `seq`.
    - A pull with nothing new answers the family's seq (below `since` if the server lost data), plus `restored` after `admin.js restored` (`families.restore_gen`, `restored_seq`).
    - New data must use the current epoch, deletions too.
    - Tombstones may carry a sealed body or (older apps) none; anything else needs data.
    - Records must be written as the calling device.
  - WebSocket `live?token=` sends data-free notifications (`seq`, `log`, `keys`, `invite`). At most 4 sockets per phone (the oldest go); errors while connecting close the socket instead of reaching Nest (an unhandled rejection would end the process).
  - `push/token` (PUT/DELETE, `{token, platform}`): kept only with `PUSH=fcm` (the default for `MODE=hosted`; needs `FCM_SERVICE_ACCOUNT`, a Firebase service-account key, mounted from `./secrets` in Docker). After accepted writes, `PushService` sends the family's other Android phones a data-only, high-priority `{kind: 'sync'}` message straight to FCM HTTP v1 (coalesced over 2 s; OAuth token from a JWT signed with the key via `node:crypto`, cached for the hour). Tokens are dropped on FCM 404/400 or when the device is removed. iOS: with `APNS_KEY` (+ `APNS_KEY_ID`, `APNS_TEAM_ID`; `push/apns.ts`), a content-free background push (`apns-push-type: background`, priority 5, `content-available`) over `node:http2` with an ES256 provider token (cached 50 min); production first, the sandbox on `BadDeviceToken` (development-signed builds), so the app doesn't say which; 410/`BadDeviceToken` in both drop the token. A platform the server can't reach keeps its tokens unsent. A push key that doesn't load (missing, unreadable, not a key) turns that push off with an error in the log, and the server starts anyway (a malformed `apns.p8` once crash-looped production). Push only reaches app builds made with the same Firebase project (Apple team and bundle id). `/v1/info` reports `push` (FCM or APNs).
- **Payments** (hosted only, `MODE=hosted`; PROJECT.md §3; `purchases/`, `sync/entitlements.ts`):
  - `Entitlements.family` works out each active phone's `SyncAccess`, in join order (`devices.added_at`): its own `unlock`, else one of the family's gifted `slot`s (handed out in join order, so a removed phone's slot passes on), else `trial` (14 days from `families.created_at`), else `grace` (48 h after the trial or after joining, if later), else `readOnly`. Self-hosted: `free`.
  - A `readOnly` phone gets 402 on `sync/push` and blob uploads; pulling, the log and keys still work. Photos stop at 2 GB per family (`canStore`, 403).
  - `GET /v1/entitlement` (also the photo use and allowance, and `inactiveDays` when the server deletes quiet families); `POST /v1/purchases {store, product, token}` verifies with the store, stores a `purchases` row (`google:`+sha256(token) or `apple:`+originalTransactionId; no personal data), then acknowledges (unlock) or consumes (slot) on Google. An unlock moves to whichever phone sends it (a restore); a slot belongs to the buyer's family for good. Changes publish a live `entitlement` message.
  - Google: the Android Publisher API with a service account (`common/google.ts` `GoogleAuth`, shared with FCM push); refunds from `voidedpurchases`, checked hourly by Housekeeping.
  - Apple: StoreKit 2 JWS checked offline against the embedded Apple Root CA G3 (`purchases/appleRoot.ts`; x5c chain, Apple's marker OIDs, ES256); refunds from App Store Server Notifications V2 at `POST /v1/purchases/apple/notifications`. Sandbox purchases only with `APPLE_ALLOW_SANDBOX=1`.
  - Test store (`TEST_PURCHASES=1`, never on the official server; `/v1/info` reports `testPurchases`): accepts any `test-…` token the app makes up, plus `POST /v1/purchases/test/refund`. The app uses it (release builds too) whenever the server offers it.
  - `node dist/admin.js restored` after restoring a backup (README "Restoring a backup"): counts up every family's `restore_gen` and notes its seq.
  - Grants: `node dist/admin.js status | grant-slots <family> [n] | revoke-grants <family>` inside the container (`src/admin.ts`, a second esbuild entry): slots with `store: 'grant'` and no buyer, for our own family, support and press. No HTTP endpoint.
  - Product ids: `PRODUCTS` in `protocol.ts` (`sync_unlock` non-consumable, `sync_slot` consumable). The e2e suite runs a hosted app against a fake Play API and an openssl-made Apple chain (`test/appleCerts.ts`).
- **Recovery-key sessions** (`deviceId === 'recovery'`) may only read the log and keys, append an `add`, grant (only to a phone the recovery key added; grants are first-come), and delete the family. They can't sync or rotate.
- **Code conventions:**
  - No `emitDecoratorMetadata` (tsx/esbuild/vitest don't emit it): always inject with an explicit `@Inject(Token)`.
  - `lockFamily(tx, id)` serializes writes per family.
- **Production backups** (`deploy/production`, LAUNCH.md O2): `backup.sh` (nightly systemd timer on the server) streams `pg_dump -Fc | age` to the `S3_BACKUP_BUCKET` (daily/weekly/monthly prefixes, deleted by the bucket's lifecycle after 8/36/95 days; the script never deletes); the server only has the age public key. `ops-setup.sh` (run from the Mac) installs it and sets the bucket rules (photo bucket: versioning, 30 days); `restore-test.sh` restores into a throwaway Postgres on the Mac with `~/subby-backup.key`. Backup retention is what the privacy policy promises; change both together. **Monitoring** (O3): `monitor.sh` (every 5 min) reports `/healthz`, the website, certificates, disk and database to Healthchecks.io (`HC_PING_SERVER`), and `backup.sh` reports each run (`HC_PING_BACKUP`); both timers come from `ops-setup.sh`. `monitor.sh` also reads the server's counters and alerts on a 5xx burst or failing pushes, and once a day writes a summary of totals to `stats.log` and `HC_PING_SUMMARY`.
- **Metrics** (`common/metrics.ts`, LAUNCH.md S7): in-memory counters (requests by route pattern and outcome, pushes, purchase checks, housekeeping), Prometheus text on the container's own `127.0.0.1:8788` (`METRICS_PORT`; `?totals=1` adds database totals). Never ids, IPs or URLs in counters or log lines; count with `Metrics.count('<event>')`.
- **Single-instance assumptions:** auth challenges, rate limits and live sockets are in memory. Use Postgres LISTEN/NOTIFY to scale out.
- **Housekeeping** (`common/housekeeping.ts`, hourly): deletes expired sessions and invites more than a day past expiry. Hosted: families without a pull for `INACTIVE_DELETE_DAYS` (365) are deleted like `DELETE families/me`; from `INACTIVE_WARN_DAYS` (335) their Android phones get a sync push at most weekly (`inactivity_pinged_at`). Pulls refresh `families.last_active_at` at most daily.
- **Shutdown:** Fastify runs with `forceCloseConnections: true`, and `LiveGateway` terminates its sockets on destroy. Otherwise a connection that never sent a request (or a closing WebSocket) holds a restart for up to the 60 s header timeout; that was the flaky e2e teardown.
- **Bodies before a session** (`common/bodyGate.ts`): a request with a body needs a valid session before it's read (the guard reuses that lookup), except on the open routes (auth challenge/verify, creating a family, claiming an invite and its status, Apple's notifications), which take at most `OPEN_BODY_LIMIT` (64 KB). A new unauthenticated route with a body goes in `OPEN_ROUTES`, or it answers 401.
- **Rate limits** (`common/rateLimit.ts`): token buckets per rule and client IP, in memory and bounded (least recently used dropped). Tight on unauthenticated or costly routes (auth, family create, invites, claims, blob uploads, push tokens), generous for the rest; 429 with `Retry-After`. `RATE_LIMIT=off` disables them (the e2e suite does, since every simulated phone is 127.0.0.1). WebSocket upgrades skip Fastify's hooks, so `LiveGateway` limits opening live sockets per IP itself (`LIVE_LIMIT`).
- **Behind a proxy:** `TRUST_PROXY` is Fastify's `trustProxy` (proxy addresses or ranges, e.g. `uniquelocal` for Caddy in the compose; `true` is refused, since any client could then pick its IP). Without it, every request seems to come from the proxy.
- **Query parameters:** numbers are parsed with `queryInt` (whole numbers only, at most a 32-bit integer unless a larger `max` is given, otherwise 400).
- **Input bounds** (`protocol.ts`): base64url fields are length-capped and refuse lengths that can't decode (4n+1); epochs and log indexes fit 32 bits; grant and rotate lists are capped. Auth challenges are capped in memory (oldest dropped); live sockets have a 4 KB message limit and aren't tracked if they closed during auth.
- **Modes:** `MODE=self|hosted`. Hosted adds payments and the photo allowance (see Payments above).
- **Commands** (in `apps/server`):
  - `pnpm db:up`: dev Postgres on port **54329** via `docker-compose.dev.yml`.
  - `pnpm serve:dev`: needs `.env`, copied from `.env.example`. Deliberately not named `dev`, so the root `pnpm run dev` still only starts the app.
  - `pnpm build`: esbuild bundles the shared package; npm dependencies stay external.
  - Schema changes: edit `src/db/schema.ts`, then run `pnpm db:generate`. Migrations run at startup.
- **Docker / self-hosting** (`apps/server/README.md`):
  - `Dockerfile` builds from the repo root (`.dockerignore` keeps only the app's `package.json`).
  - The runtime stage installs only the server's npm dependencies, pinned from `pnpm list`. Don't use `pnpm deploy`: drizzle-orm's optional peers, shared with the app in the lockfile, pull in React Native (over 1 GB).
  - `docker-compose.yml` runs server + Postgres, with an optional `https` profile (Caddy, `DOMAIN`). Settings go in `docker.env.example` → `.env`.
    - With HTTPS, set `HTTP_BIND=127.0.0.1` so plain HTTP isn't reachable around Caddy.
    - The dev Postgres binds to 127.0.0.1 only.
    - Android Auto Backup only includes shared preferences (minus SecureStore), via expo-secure-store's rules. Photos and the database are never in Google backup; keep it that way if backup rules change.
  - Verified locally: the full client flow against the container (pair, sync, photo, live).
- **Tests:** `test/e2e.test.ts` runs the real server on a throwaway database. `test/client.ts` is a full simulated app (pairing, sync, removal + rotation, recovery) and the reference for the mobile sync engine. The tests are skipped, with a warning, when the dev Postgres isn't running.

### Native builds (local, no EAS)
- `expo-dev-client` is installed, so `pnpm run dev` / `expo start` now targets the **Subby dev build**. Use `pnpm --filter @subby/mobile dev:go` (or press `s`) for Expo Go.
- `android/` and `ios/` are generated (Continuous Native Generation) and gitignored. Never edit them: change `app.json` or a config plugin instead.
- Build and install on a USB-connected phone or an emulator: `cd apps/mobile && pnpm android`. After native changes (new native package, `app.json` plugins), run `pnpm android:clean`.
- Rebuild only for native changes; JS changes hot-reload as usual.
- **Release builds don't notice changes in `packages/shared` alone**: Gradle's JS bundle task only watches the app, so after a shared-only change run `./gradlew :app:createBundleReleaseJsAndAssets --rerun` first (or the APK ships the old bundle).
- **Release builds** (`./gradlew assembleRelease`): Gradle runs the Expo CLI directly, without pnpm's `NODE_PATH`, so Babel resolves presets from `apps/mobile/node_modules`. That's why `babel-preset-expo` and `@babel/plugin-transform-react-jsx` (named by NativeWind's preset) are direct devDependencies; keep them.
- **Standalone builds for a LAN server**: `app.config.js` adds `usesCleartextTraffic` (via `expo-build-properties`) only when `SUBBY_ALLOW_HTTP=1` is set during prebuild: `SUBBY_ALLOW_HTTP=1 npx expo prebuild --clean --platform android && (cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a,armeabi-v7a)`. Release APKs are signed with the debug key unless `SUBBY_SIGNING=/path/to/upload.properties` is set during prebuild (`plugins/withReleaseSigning.js`: Gradle reads `storeFile`, `storePassword`, `keyAlias`, `keyPassword` from that file at build time; keystore and file live outside the repo). Debug-signed release APKs install over the dev build and keep the data; upload-signed ones don't. Never set the switch for a store build: the local `android/` is usually prebuilt with it (for the LAN server), so run `npx expo prebuild --clean` without it before building anything for a store.
- **iOS on a device** (team `L33LRKM2NX`, automatic signing): `npx expo run:ios --device` can't register a new device or create its profile. For a new device, build once with `cd ios && xcodebuild -workspace Subby.xcworkspace -scheme Subby -configuration Debug -destination 'id=<udid>' -allowProvisioningUpdates -allowProvisioningDeviceRegistration -derivedDataPath build build`, then `xcrun devicectl device install app --device <udid> build/Build/Products/Debug-iphoneos/Subby.app`. The device needs Developer Mode, and no Apple ID. "Unable to verify app" after an iPadOS update went away with an uninstall and reinstall. iOS keeps Keychain items (SecureStore) across an uninstall: turn sync off before deleting the app, or the reinstall comes back with the old sync identity.
- **Background tasks don't run headless in dev-client builds** (the headless runtime can't load the bundle from Metro). Test them in a release build. Release builds block `http://`, so test against an https server, or temporarily allow cleartext in the generated manifest.
- Toolchain (Android): JDK 17, Android SDK 36, build-tools 36.0.0, NDK 27.1.12297006 (Gradle fetches the NDK). `JAVA_HOME` and `ANDROID_HOME` must be set.
