# Launch plan

Everything left before Subby and the hosted Subby Sync (`sync.subby.baby`) launch together. There is no public beta: we test it ourselves on the production server before release. Written 2026-11-05. Tick items off here as they land.

IDs: **D** decisions, **S** server, **A** app, **P** payments, **O** operations, **L** legal, **R** store release. Dependencies are in brackets.

## Decisions first

These block tickets further down.

- [x] **D1 What's paid** (decided 2026-11-05).
  - The app is free and complete on its own. A single parent keeps everything on the phone, with the backup file for safety. The server is only for sharing: either the hosted Subby Sync (paid) or self-hosted (free).
  - **No free phone.** Every phone that syncs on the hosted server needs an unlock, bought once, in one of two ways:
    - **Its own unlock:** a non-consumable purchase on the person's store account. It's restorable on a new phone and comes along into any family; the server records which phone uses it, one at a time.
    - **A gift from the family:** any member buys a slot (a consumable). The slot belongs to the family, frees up when its phone is removed, and works on Android and iPhone alike.
  - **Price:** €6.99 per phone, the same for both kinds. No bundle.
  - **Trial:** a family syncs fully for 14 days from when its second phone first joins (from setup while alone; changed 2026-11-24). No card, nothing renews automatically: the trial simply ends.
  - **Grace period:** after the trial, a phone without an unlock still syncs for 48 more hours (so a partner's phone doesn't stop mid-night), then reads but can't log until it's unlocked.
- [x] **D2 Photo allowance** (decided 2026-11-05): **2 GB per family**, no add-on. Past it, new photos stay on the phone. [S3]
- [x] **D3 Caregivers** (decided 2026-11-05): no free caregiver tier. A parent can gift a slot instead (D1).
- [x] **D4 Billing** (decided 2026-11-05): **our own verification** against Google Play and the App Store, no RevenueCat. [P1]
- [x] **D5 Inactivity** (decided 2026-11-05): a hosted family with no phone syncing for **12 months** is deleted from the server. The app warns from month 11 (30 days ahead). The phones keep everything. [S4]
- [x] **D6 Platforms** (decided 2026-11-05): **Android and iOS together.** iOS hasn't been prebuilt, run on a device or given push yet, so A7–A9 and R3 are in scope. Needs the Apple developer account.
- [x] **D7 Package id** (decided 2026-11-05): **`baby.subby.app`** (Android package and iOS bundle id). The Pixels reinstall once, then restore from a backup or re-join sync. A new Firebase app registration and `google-services.json` are needed. [R1]
  - Done in code 2026-11-08: `app.json` uses `baby.subby.app`; `app.config.js` skips a `google-services.json` without a client for it (warns, builds without push). Firebase app `baby.subby.app` registered and the new `google-services.json` in place (2026-11-09); both Pixels run it, and an FCM push from `sync.subby.baby` reached the Pixel 10. A family sleep alert reached a swiped-away Pixel 10 about 20 s after the other phone logged it (2026-11-11: push, headless start, login, sync, notification).
- [x] **D8 Hosting** (decided 2026-11-05): **Hetzner, Germany**. A Cloud VPS running the existing Docker compose (Postgres self-run), Hetzner Object Storage for photo blobs (`BLOB_STORE=s3`), nightly encrypted Postgres dumps to a separate bucket. [O1, O2]
- [x] **D9 Crash reporting** (decided 2026-11-05): **store consoles only** (Play Console, App Store Connect). No SDK. A10 is dropped.
- [x] **D10 Android ↔ iPhone** (decided 2026-11-05): an own unlock stays with its store (switching means buying again); gifted slots work on both.
- [x] **D11 Tip** (decided 2026-11-05): not at launch.
- [x] **D12 Push** (decided 2026-11-05).
  - Hosted: included (FCM done, APNs = A9). On iOS the content-free push is a background push that iOS may delay, so family alerts on iPhones can be late.
  - Self-hosted: no push at launch (live sync while open, OS background sync, "check the app first" on medication reminders).
  - **After launch:** a free, rate-limited push relay through `sync.subby.baby`, which the self-hoster switches on. It sees only push tokens and timing. UnifiedPush only if asked for.
  - Local reminders never need push.

## Server (Subby Sync)

- [x] **S1 Rate limiting** (per client IP; `common/rateLimit.ts`). On `auth/challenge`, `auth/verify`, `invites` (create, claim, status), `families` (create), blob uploads and push token registration. In memory is fine (the server is single-instance).
- [x] **S2 `trustProxy`** for Fastify behind Caddy, so limits and logs see the real client IP. Off by default for self-hosters without a proxy.
- [x] **S3 Photo allowance.** `Entitlements.canStore` sums the family's blob sizes in hosted mode. Self-hosted stays unlimited. [D2]
- [x] **S4 Inactive-family cleanup.** Done 2026-11-11: pulls keep `families.last_active_at` (at most daily); Housekeeping (hosted) wakes a family's Android phones with a sync push weekly from day 335 and deletes it after 365 days without a pull (`INACTIVE_*_DAYS` in protocol.ts). The warning itself is local (A4), since a phone that doesn't sync can't hear the server. **Must be done before hosted sync opens:** subby.baby (/sync/, /privacy/) already promises deletion after 12 months with a warning in the app from month 11. Track the last sync per family; housekeeping warns (a live/push message the app shows) and later deletes. Deleting a family also deletes its gifted slots, so the warnings must say so. [D5, S5]
- [x] **S5 Deleting a family's data.**
  - When the last phone leaves, delete everything: records, keys, the device log, blobs, push tokens and the family row.
  - ~~Also a "Delete this family from the server" action in the app, for any member.~~ Decided against (sync.md): one phone shouldn't end sync for everyone in one tap; the last phone leaving deletes the family.
  - ~~App: Sync settings button with a type-to-confirm.~~ Not built (see above).
- [x] **S6 Hosted-mode entitlements.**
  - A family's trial start (14 days from creation), plus a 48-hour grace per phone after the trial ends.
  - Own unlocks (purchase → the phone currently using it), and gifted slots (a count per family, each assigned to a member phone, freed on removal).
  - `canSync` per device: in the trial, or with an own unlock or an assigned slot → push allowed; otherwise pull only.
  - Self-hosted mode always allows everything. [D1, P1]
- [x] **S7 Metrics and logs without user data.** Request counts, error rates, family/blob totals; never ids or IPs in long-lived logs. `/healthz` done (Postgres and photo storage); Caddy keeps no access log.
  - Plan (2026-11-10, before A14 and the dogfood run): in-memory counters per route and outcome (requests, 4xx, 5xx), pushes sent/failed, purchase checks, reachable only from the server itself; `monitor.sh` fails on a 5xx burst and sends a daily summary of totals (families, phones by access, photo storage, requests), no ids or IPs. In the app, "Copy diagnostics" for support (version, sync status, last error, counts; nothing personal, nothing sent by itself). No analytics or crash SDK (D9).
  - Built 2026-11-10: `common/metrics.ts` counts requests by route pattern and outcome, pushes (sent, failed, tokens dropped), purchase checks per store and outcome, refunds and inactive families; Prometheus text on the container's own `127.0.0.1:8788` (`METRICS_PORT`), `?totals=1` adds families, phones by access, records, photos, push tokens, recovery keys. `monitor.sh` reads it each run: ≥ 5 server errors in 5 min, or ≥ 3 failed pushes and none sent, is a `/fail`; the status line has the requests; once a day the day before's summary goes to `stats.log` and `HC_PING_SUMMARY` (optional third check, period 1 day). A blob id left a warning log line (removed). App: Settings → Help → "Share diagnostics" shows the report (version, system, counts, reminders, background, sync status, last error, access, photo use; no names, ids or own-server address) and shares it only on request (system share sheet, no clipboard module). Deployed 2026-11-10, `HC_PING_SUMMARY` set, the report checked on a phone.
- [x] **S8 Dependency refresh** before launch (NestJS 12.2+ / fastify 5.12.7 clears the open low advisory), and `pnpm audit`. Done 2026-11-12: server on NestJS 12.5.0 / fastify 5.12.8 (clears the server's only advisory), ws, the S3 client; the app on the latest SDK 57 patches (`expo install --fix`); vitest 5.1 everywhere. Left by choice: `postgres` 4, TypeScript 7 on the server and `@types/node` 26 (majors; the server runs Node 24), and **Expo SDK 58** (out now). Decided 2026-11-12: these majors wait until after launch (X4). What `pnpm audit` still lists (26) is build tooling that never ships (node-forge and zod 3 in `@expo/cli`, uuid and deepmerge in the config plugins, glob, minimatch, esbuild in drizzle-kit, postcss-selector-parser in Tailwind), except `decode-uri-component` 0.2.2 under expo-router's `query-string`, which is in the app: a crafted `subby://` link could make URL parsing slow (the app freezes, nothing leaks). The fixed versions are ESM-only and expo-router `require`s it, so it waits for Expo.
- [x] **S9 Far-future `updatedAt` (audit S-7 leftover).** Done 2026-11-12: pulls carry the server's time; a phone more than 5 min off shows a warning on Home and the Sync screen (and in diagnostics). The server refuses records dated more than a day ahead (`MAX_CLOCK_AHEAD_MS`, answered as stale), so they stay pending on that phone instead of beating every later edit, and the app re-dates pending edits from the future once its clock is right. A clock running behind only gets the warning (indistinguishable from a late edit). DST checked at the same time: durations are real time, days are local calendar days; `dst.test.ts` covers both 2026 changes, the shared tests run with `TZ=Europe/Berlin`.
- [x] ~~**S10 Moving between servers, robustly**~~: dropped with Move itself (A18, decided 2026-11-28). Its gaps, for if Move ever comes back: moving back to a server the family left, an interrupted move blocking every retry, leaving the old family never retried, and the move running outside the sync lock (a run still going against the old family writes into the new one's settings).
- [x] **S12 Restoring a backup without the families noticing** (2026-11-10). After `admin.js restored`, phones give back the device log entries, photos and records the server lost and pull everything again; old-key records written after the backup are refused (restore floors). e2e: backup, a join, a removal and writes after it, restore, a removed phone writing in between. Left as is: a family whose phones all joined after the backup sets up sync again (indistinguishable from a deleted family); purchases after the backup need a store restore (P1/A3: the app should re-send its purchases when its access looks wrong); photo files uploaded after the backup whose rows weren't given back stay in the bucket (a sweep of files without rows would catch them).
- [x] **S11 Request limits left from the review.** Finished 2026-11-12: live sockets are limited per client IP in the gateway (30/min, before the token lookup; the IP as Fastify sees it, via `@fastify/proxy-addr` and `TRUST_PROXY`); a body gate (`common/bodyGate.ts`) checks the session before any body is read, except on the open routes (auth, creating a family, claiming an invite, Apple's notifications), which take at most 64 KB, counted as it arrives when there's no length; Caddy caps bodies at 24 MB. Before that: rate limits match the decoded path, malformed tokens are refused without a query, a failed live socket can't crash the process, at most 4 sockets per phone, 5-minute request timeout. Left: a per-IP limit on WebSocket upgrades (needs the same `trustProxy` IP logic as Fastify), and refusing unauthenticated requests before their body is read (large bodies only on the push and blob routes). Check Caddy's `request_body max_size` too.
- [x] **S13 Audit 2026-11-21 (Gemini), server side.** Triaged 2026-11-21; false or by design: the Ed25519 verifier mismatch (both verifiers tested to agree), the zip bomb (fflate stops at the declared size), lock-screen visibility.
  - Done 2026-11-21: SEC-05 (a deleted `moved` record got past the 402 and the family caps; deleted moves now count), SEC-04 (member bodies 64 KB except `LARGE_ROUTES`, raw bytes only for photos, large bodies in flight capped per phone and server-wide), SEC-06 (the production compose passes the server only its own variables; the backup keys and ping URLs stay on the host). **Deploy, then check `/healthz`, a push and a photo upload.**
  - Done 2026-11-21, the rest: SEC-13 (a limiter per rule; open creating/claim/auth routes also per IPv6 /48), SEC-14 (push tokens only for active phones under the family lock and dropped by token, a live socket checked again once tracked, a photo written after its family was deleted is removed), SEC-22 (indexes on `devices`, `sessions`, `invites`, `push_tokens`, migration 0009; per-token push errors; 15 s timeouts for FCM, Google OAuth (one at a time) and Play), SEC-23 (old pre-deploy dumps swept nightly; kept unencrypted for a quick rollback), small-order X25519 box keys refused in the device log, `keys` for a deleted family answers 401. Left as is: the daily totals' per-family queries (once a day), the challenge used before the lock (a retry asks for a new one).

- [ ] **A19 Sync requests time out** (REVIEW.md 4b; before launch). React Native's Android HTTP client has no timeouts at all (`OkHttpClientProvider`: connect, read and write 0), and `call()` and `raw()` pass no signal, so a stalled connection hangs a run for good: every later `syncNow()` waits on it until the app is killed (iOS gives up after 60 s). Add `AbortController` timeouts that fit the request: pushes go up to `MAX_REQUEST_BYTES` (16 MiB) and photos to `MAX_BLOB_BYTES` (20 MiB), minutes on a slow upload, so a fixed 30 s / 120 s (the review's proposal) would fail them on every run. Scale with the body size, or time out when nothing moves. A timeout is a `SyncHttpError(0)` (retried with backoff). Check that `expo/fetch` honours the signal. The session can abort its requests (A20). Test: a server that accepts and never answers.
- [ ] **A20 Turning sync off waits for the run in flight** (REVIEW.md 1; before launch). `turnOffSync` clears the settings while a run may still be going with its own settings and session. Then the run sets the phase back to `idle` (with members) after sync is off, and its family alerts and inactivity warning can land after the cancel. If the phone sets up, joins or recovers before that run ends (likely only with a hung request, A19), the run's `saveSync` writes land on the new family's row: `lastSeq`, and `pulledEpochs` from an old family that ever rotated, after which every record of the new family's epoch 1 is refused, silently. Fix: turning off aborts the session's requests and waits for `running` before `forgetSync`; setup, join and recovery wait for it too. Belt and braces: `saveSync` takes the family id a patch is meant for and drops it on another family's row. `forgetSync` also resets `failures`, `quiet` and the pulled logs.
- [ ] **A21 No redundant sync runs** (REVIEW.md 2, A16's leftover; before launch). A run that applies anything reloads the stores, and `useSyncEngine` takes `hydrate` (a new `children` array) and `loadLogs` (`revision`) as local writes: one more, empty run 1.5 s later. Switching child and `loadOlder` start a run too. And the server's live message goes to every socket in the family, the pushing phone's own included (`LiveBus.publish`), so every run that pushes starts another 300 ms later. Fix: a `writeRevision` on `useLogStore` and `useChildStore`, bumped only by local writes, for `useSyncEngine` to watch (`revision` stays: `useLogQuery` re-reads on it); the server leaves out the pushing phone's sockets (needs a deploy).
- [ ] **A22 Settings read before an await, saved after it** (REVIEW.md 5; small, before launch). Build each patch from `syncSettings()` after the last await (an updater form of `saveSync`).
  - `refreshMembers` compares with the run's `settings.knownDevices`, not the fresh row: when `heal` runs it a second time in the same run, "New phone in your family" names the phone twice, and a run that started before `approveClaim` saved can flag the phone just added.
  - `removeDevices` saves `names` from before `rotateKeys`, which pulls: a rename pulled there is lost for good (`nameVersions` keeps it from coming back). The same pattern with a smaller window: `pushDeviceName` (names, versions, tags), `approveClaim` (`knownDevices`), `setUpBackgroundSync` (`push`, `pushToken`).
  - `refreshKeys` loads the keys, awaits the server, then saves the whole map: a rotation saved in between is overwritten (the next run heals it, since the key is sealed to this phone too). Re-read before saving.
- [ ] **A23 Small sync items** (REVIEW.md 4, 6, 7b, 8; may wait until after launch).
  - Live: stop retrying (every 30 s while open) after `IdentityLostError` or a removal; on 4401 with a cached token (sessions last 7 days) log in again once before giving up, since today live stays off until the next foreground; `closeLive` resets the backoff; events from a dropped socket are ignored; a pending retry is cleared before another is set.
